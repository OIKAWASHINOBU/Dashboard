# 手順1：「ページにリダイレクトがあります」の切り分け

## まず結論：全部が異常ではありません

Googleのメールにも「**これが意図したものでない場合は**、修正することをおすすめします」
と書かれている通り、この項目は **正常な転送も同じ場所に集計されます**。
やみくもに転送を消すと、かえって順位を落とします。

やるべきことは「転送を消す」ことではなく、
**Googleに拾わせるURLを、最初から転送先（最終URL）に統一する** ことです。

---

## Step 1. 対象URLを一覧で取り出す

1. Search Console を開く
2. 左メニュー **［インデックス作成］→［ページ］**
3. 「ページがインデックスに登録されなかった理由」の中の
   **「ページにリダイレクトがあります」** をクリック
4. 表示されたURL一覧の右上 **［エクスポート］→［CSV をダウンロード］**

CSVがあれば、下の判定表に機械的に当てはめられます。

---

## Step 2. 判定表（この表だけで9割片付きます）

### 🟢 放置してよい（正常な転送）

| URLの見た目 | 何が起きているか |
|---|---|
| `http://` で始まる | https版へ転送。**正常**。SSL化すれば必ず出ます |
| `www` の有無が正規と違う | 正規URLへ転送。**正常** |
| `?attachment_id=123` / 画像名だけのURL | 添付ファイルページ→親記事への転送。**WordPressの標準動作** |
| `/feed/` `/trackback/` `/?p=123` | 内部用URL。**正常** |
| 終了したキャンペーンLPの旧URL | 意図的な301。**正常** |
| 大文字/小文字違い、末尾スラッシュ違い | 正規化転送。**正常** |

→ これらは **報告として出続けますが、順位への悪影響はありません。** 放置で構いません。

### 🔴 直すべき（意図しない転送）

| 症状 | 原因 | 対処 |
|---|---|---|
| **転送が2段以上**（A→B→C） | 301チェーン | A→C の1段に書き換える（下記 Step 4） |
| **転送が循環している**（A→B→A） | 一般設定とプラグインの二重リダイレクト | Step 3 を実施 |
| **サイトマップに旧URLが載っている** | パーマリンク変更後の再生成漏れ | SEOプラグインでサイトマップ再生成 |
| **サイト内リンクが旧URLを指している** | 記事本文のリンク貼り替え漏れ | 本文を最終URLに一括置換 |
| **短縮URL（x.gd 等）がサイト内リンクにある** | 短縮サービス自体が転送 | **サイト内リンクには短縮URLを使わない**（広告・SNS用に限定する） |
| **canonicalタグが転送元URLを指している** | プラグイン設定ミス | canonicalは必ず最終URLに |
| **公開したばかりの新記事が出ている** | 上のどれでもない、本当の異常 | Step 3〜4 |

---

## Step 3. WordPress側の二重リダイレクトを止める

「転送が循環している／2段以上」の場合、原因はほぼこの3つです。

### 3-1. 一般設定を確認

**［設定］→［一般］**

- **WordPress アドレス (URL)**
- **サイトアドレス (URL)**

この2つが **完全に同一** で、**https://** で始まり、**末尾スラッシュなし**、
**www の有無が揃っている** ことを確認してください。

```
✅ 良い例   https://example.co.jp
❌ 悪い例   http://example.co.jp        （httpのまま）
❌ 悪い例   https://www.example.co.jp/  （もう一方が www なし・スラッシュ有）
```

### 3-2. SSL化プラグインと .htaccess の重複

`Really Simple SSL` などのSSL化プラグインを入れたまま、
`.htaccess` にも https 強制ルールを書くと **二重に転送**されます。

→ **どちらか一方だけ** にしてください。推奨は `.htaccess` 側
（サーバーレベルで処理されるため速い）。プラグインのリダイレクト機能はオフに。

### 3-3. リダイレクトプラグインのチェーン検査

`Redirection` プラグインを使っている場合：

**［ツール］→［Redirection］→［ログ］** で、同じURLが連続して転送されていないか確認。
転送元→転送先が、さらに別の転送ルールに引っかかっている場合は、
**中間を飛ばして最終URLへ直接転送する1本のルール** に統合します。

```
❌ /old-a  →  /old-b  →  /new     （2段）
✅ /old-a  →  /new                 （1段に統合）
   /old-b  →  /new
```

---

## Step 4. サイトマップと内部リンクを最終URLに揃える

ここが **今回の警告に対する本丸** です。

### 4-1. サイトマップの再生成

SEOプラグインの設定で、**サイトマップに含めない**ものを外します。

| 除外するもの | 理由 |
|---|---|
| 添付ファイル（メディア） | 転送されるだけの空ページ |
| タグアーカイブ（使っていない場合） | 中身の薄い重複ページ |
| 著者アーカイブ（1人運営の場合） | トップと重複 |
| 検索結果ページ・404 | インデックス不要 |

その後 `https://example.co.jp/sitemap.xml`（プラグインによりファイル名は異なる）を
ブラウザで開き、**転送される古いURLが載っていないか** 目視確認してください。

### 4-2. 内部リンクの一括置換

`Search Regex` プラグイン、または `Better Search Replace` プラグインで、
記事本文中の旧URLを新URLに置換します。**必ず先にデータベースのバックアップを取得**。

置換対象の代表例：

```
http://example.co.jp        →  https://example.co.jp
https://www.example.co.jp   →  https://example.co.jp
https://x.gd/xxxxx          →  （本来の遷移先URL）
```

### 4-3. Search Console に再検査を依頼

1. Search Console 上部の検索窓に、直したURLを貼って **URL検査**
2. 「**インデックス登録をリクエスト**」をクリック
3. 一覧の再クロールは **［検証を開始］** ボタンから依頼

反映には **1〜4週間** かかります。翌日に変化がなくても正常です。

---

## Step 5. 直った状態の確認方法

ブラウザだけで確認する場合は、リダイレクトチェッカー（`redirect checker` で検索）に
URLを入れて、**200 が1回で返る**ことを見ます。

コマンドが使える場合：

```bash
curl -sSI -L -o /dev/null -w '%{num_redirects} 回転送 → 最終 %{http_code} %{url_effective}\n' \
  https://example.co.jp/
```

- `0 回転送 → 最終 200` … 理想
- `1 回転送 → 最終 200` … 許容（http入力時など）
- `2 回以上` … チェーン。Step 3-3 へ
